# Factory harness

The code that turns a ready issue into a reviewed pull request with evidence. A change here is a harness change: the Factory labels it `harness-change` and warns on the PR. Repo rules are in the root `AGENTS.md`; terms are in `GLOSSARY.md`.

## Layout

- `src/cli.ts`: `pnpm factory <claim|work|publish|local>`. `src/commands/`: one file per command.
- `src/adapters/`: the four seams, each with a real and a fake adapter: `Tracker`, `CodeHost`, `Agent`, `Verify` (interfaces in `src/seams/`). `local/` is the Markdown tracker and local code host, `sandcastle/` the real Agent.
- `src/bootstrap/`: `pnpm bootstrap [doctor [<id>]] [domain <id>] [product <id>] [previews <id>] [--redo <step>]`. Wizard steps in `common.ts` (common part), `product.ts` (the Production module of `bootstrap product <id>`) and `domain.ts` (per Product: `resend-domain`, `dns-records`, `restricted-resend-key`, `worker-domain`; `resendSteps(product)` is reused by `bootstrap product`, `domainSteps` adds `worker-domain` for `bootstrap domain` only: the Worker does not exist before the first deploy) over client interfaces (`clients.ts`: GitHub, Cloudflare, Neon, Resend), real adapters (`cloudflare.ts`, `resend.ts`, Zod-validated; `neon.ts` drives `neonctl`) and `fake/`. `previews.ts` is the Previews module (`previewSteps`). `github.ts` is the only module that calls `gh`. Resend is optional: before any key prompt the wizard asks once "Set up real email with Resend now?" (default: skip, keeps the outbox; `RESEND_API_KEY` in the env skips the question; no TTY defers). Setting it up prints `https://resend.com/api-keys` and asks for the key, empty = deferred. A blank credential is never re-asked in the same run (`memory.resendDeferred`, `memory.cloudflareDeclined`). No local state, no secret on disk; `doctor` only reads. The wizard (common and `domain`) ends by running the doctor with the credentials held in memory (exit code = doctor); standalone, with a TTY and no `CLOUDFLARE_API_TOKEN`/`RESEND_API_KEY` in the env, the doctor asks once (hidden, not stored); without a TTY it says `skip`.
- `src/ci/`: logic of the workflows, thin YAML around it: `image.ts`, `matrix.ts`, `skills.ts` (PR) and `deploy.ts` (plan, bundle, allowlist check, config, migrate) plus `smoke.ts` (the `main` deploy, `.github/workflows/factory-deploy.yml`; `--preview` is the smoke of a PR preview), `previews.ts` (the PR previews: gate, bindings check, Neon branch, preview config, URL, result, comment, `base`, cleanup; `factory-pr.yml` and `factory-pr-cleanup.yml`) and `neon-api.ts` (the Neon branches API, `fake/neon-api.ts` is its fake).
- `src/config.ts`: every setting and the label vocabulary. Any leaf is overridden by a `FACTORY_*` repo variable.
- `src/guard.ts`: the deterministic guard before the lock. `src/paths.ts`: protected and harness paths. `src/result.ts`: the Zod schema of `result.json`.
- `src/report.ts`: PR, review, evidence and Escalation text. `src/prompts.ts` renders `prompts/*.md`.
- `prompts/`: the Stage prompts (`development`, `review`, `triage`, `pr-feedback`, `update-branch`) plus `rules.md`, included in every one.
- `image/`: `Dockerfile` and `setup.sh` of the execution image. `src/local/`: the local container runner.
- `test/`: Vitest, driven through the CLI with fake adapters.

## Rules

- Bootstrap steps query the real state first and only add: never delete or overwrite a DNS record. Values the person must copy are logged as one plain line, not in a clack note (notes wrap).
- Behaviour changes come with a test against the fake adapters (the CLI is the seam), not against internals.
- The Factory never trusts the event payload: each run reads the current state of the forge, and `publish` checks again before writing.
- `work` has no `FACTORY_TOKEN`. The Agent env is an allowlist (`PATH`, `HOME`, Claude auth, `DATABASE_URL`, `CI`); adding a variable needs a test that proves nothing else leaks.
- Protected paths (`.github/workflows/`, `.agents/skills`, `.claude/skills`, `.claude/hooks`, `skills-lock.json`, `.claude/settings.json`, `.mcp.json`) end in an Escalation without a PR. `src/paths.ts` must match the `deny` rules of `.claude/settings.json`; a test checks it.
- Label names exist only in `src/config.ts` and the "Factory labels" table of `docs/agents/triage-labels.md`; a test keeps them equal. Change both.
- Prompts are English templates with placeholders. They call skills by name and repeat the hard rules; they never copy a skill's text.
- The image tag is a hash of the versions it installs; bump a version only after checking the official docs.
- Untrusted text (issue, comments, review threads) is wrapped in tags in prompts and never treated as instructions.

## Commands

- `pnpm bootstrap`, `pnpm bootstrap doctor`: set up (ending with the doctor, one run is enough) and check the copied repo (needs `gh` logged in; tests use the fake clients only).
- `pnpm bootstrap product <id>`: the Production module. Steps `neon-project`, `github-environment`, `database-secrets`, `auth-secret`, the four `domain` steps, `main-ruleset`, `deploy-products`; then the doctor of the Product, and only if it passes `DEPLOY_ENABLED=true`. Secrets are `<ID>_DATABASE_URL` (direct, migrations), `<ID>_DATABASE_URL_POOLED` (the Worker), `<ID>_BETTER_AUTH_SECRET`, `<ID>_RESEND_API_KEY`, in the `<id>-production` environment (restricted to the default branch), or at repo level with `FACTORY_USE_ENVIRONMENTS=false` when GitHub refuses environments. An existing ruleset that already covers the default branch (PR, no force-push, no deletion, check `verify`) is reused, never duplicated. Neon: the wizard uses neonctl's own saved login (`neonctl auth` opens the browser only when `neonctl me` shows none, so once per machine) or `NEON_API_KEY` from the env, and passes the connection strings straight to `setSecret`; it never logs out. It makes no Neon API key for production (the deploy only needs the connection strings).
- First deploy of a new Product: a push deploys only the Products it affects, so after `bootstrap product <id>` run the Deploy workflow by hand once (`gh workflow run factory-deploy.yml --ref main`); a manual run deploys every Product in `DEPLOY_PRODUCTS`. The wizard prints this line at the end.
- `pnpm bootstrap previews <id>`: the Previews module (optional, after Production). Steps `preview-environment` (`<id>-preview`, restricted like production, same `FACTORY_USE_ENVIRONMENTS` fallback), `preview-neon-project` (`<id>-preview`, default branch renamed to `base`; variable `<ID>_PREVIEW_NEON_PROJECT_ID`), `preview-neon-key` (secret `<ID>_PREVIEW_NEON_API_KEY`, minted with `neonctl api-keys create --project-id` under the run's login; when Neon refuses, one pasted key, hidden, blank = skip and remembered), `preview-kv` (KV `<id>-preview-oauth` through the Cloudflare client; variable `<ID>_PREVIEW_OAUTH_KV_ID`) and `preview-products` (id in `PREVIEW_PRODUCTS`). Then the doctor of the previews and, only if it passes, `PREVIEWS_ENABLED=true`. The one-run rules hold: a recorded variable or secret proves a step done (no Neon login, no Cloudflare prompt on a rerun), one Neon login per run and only with Neon work. The doctor shows a Previews section for a Product by presence (any preview variable, secret, environment or the id in `PREVIEW_PRODUCTS`); the Production module never fails on it.
- PR previews (`.github/workflows/factory-pr.yml`, off until `PREVIEWS_ENABLED`): `build` (PR code, no secrets) also uploads `bundle-<id>`; `preview-plan` (`previews.ts gate`: affected ∩ `PREVIEW_PRODUCTS`, author `write`+ or the event of the `preview` label put by someone with `write`+; a push removes the label); `deploy` (`main`'s checkout, the only job with Cloudflare and Neon preview secrets; allowlist check, bindings against `apps/<id>/wrangler.jsonc` of `main`, Neon branch `preview/pr-N` from `base` or "preview skipped: limit reached" at `FACTORY_PREVIEW_LIMIT` (9) open previews, migrations, `wrangler preview --name pr-N --worker-name <id> --config <preview config> --secrets-file --ignore-base-config`); `smoke` (no secrets: real sign-up, the email read at `GET /api/preview/outbox?to=`, sign-in, `/api/me`, `/mcp` 401); `preview-comment` (one comment, edited). `factory-pr-cleanup.yml` on `closed` deletes the Worker Preview and the Neon branch. The deploy of `main` migrates `base` (`preview-base`) and recreates it when missing. The outbox route exists only with `EMAIL_TRANSPORT=outbox` and `PREVIEW_OUTBOX=true`, which only the preview config sets. A change to these workflows takes effect only after it is merged (`pull_request_target`).
- `pnpm bootstrap domain <id>`, `pnpm bootstrap doctor <id>`: a Product's domain. Reads `domain` from `apps/<id>/product.config.ts` (never rewrites it). Needs `RESEND_API_KEY` (full access, or it is asked) and the one Cloudflare token (template URL in `common.ts`: Workers Scripts Edit, Workers KV Storage Edit, Account Settings Read, DNS Edit, Zone Read; no Workers Routes, the Custom Domain needs only Workers Scripts Write; older tokens must be recreated). A pasted token is checked with read-only calls (verify, scripts, KV, account, zones, DNS records) and a refused one is named and asked again without being stored; the probes cannot tell edit from read, the first real write does. Without the zone in the account, DNS records are printed as plain lines; without the Worker, the Custom Domain waits for the first deploy.
- `pnpm --filter @factory/harness test|typecheck`
- `pnpm factory local <NN> [--issues <dir>]`: run an issue on this machine in a throwaway container (needs Claude auth).

## Cloudflare credential (never asked twice)
- The Cloudflare API token is collected once, by the `cloudflare-token` step of the common part, and only while the `CLOUDFLARE_API_TOKEN` CI secret does not exist (an explicit `--redo cloudflare-token` replaces it). `promptMainToken` is called nowhere else.
- Every other Cloudflare call (`cloudflareHandle`: previews KV, `dns-records`, `worker-domain`; `workers-dev`; the doctor) takes its credential from `cloudflareCredential` in `common.ts`, in this order: this run's memory, `CLOUDFLARE_API_TOKEN` in the env, wrangler's saved login (`wrangler auth token --json`, via `wrangler.ts`; wrangler 4.151.2 docs read 2026-10-20: refreshes an expired OAuth token itself). With none, steps that may change things run `wrangler login` once (browser; wrangler keeps it, like neonctl); the doctor and the `check`s never log in. The token stays in memory: never logged, written or sent to the forge.
- The account id is `CLOUDFLARE_ACCOUNT_ID` from the env or the only account the credential sees; with several it fails naming `CLOUDFLARE_ACCOUNT_ID`, it never asks.
- wrangler's OAuth scopes have no DNS: when listing or creating DNS records is refused (`CloudflareRefused`), `dns-records` prints each record on one unwrapped line plus a "NOT done" note and returns without prompting; run it again after creating them by hand.
