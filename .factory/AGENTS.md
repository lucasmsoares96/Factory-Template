# Factory harness

The code that turns a ready issue into a reviewed pull request with evidence. A change here is a harness change: the Factory labels it `harness-change` and warns on the PR. Repo rules are in the root `AGENTS.md`; terms are in `GLOSSARY.md`.

## Layout

- `src/cli.ts`: `pnpm factory <claim|work|publish|triage|apply|unblock|pr-feedback|update-branch|notify|local|retro-collect|retro|retro-publish>`. `src/commands/`: one file per command.
- `src/adapters/`: the four seams, each with a real and a fake adapter: `Tracker`, `CodeHost`, `Agent`, `Verify` (interfaces in `src/seams/`). `local/` is the Markdown tracker and local code host, `github/` the GitHub Tracker and CodeHost (`api.ts`: `fetch` + Zod, the token held there; `git push --force-with-lease` and `gh pr comment --attach` get it through their environment, never their argv; `markReady` is the one GraphQL call, REST has none), `sandcastle/` the real Agent. `FACTORY_ADAPTERS=github` picks them (`GITHUB_REPOSITORY`, token `FACTORY_TOKEN` else `GITHUB_TOKEN`).
- `src/bootstrap/`: `pnpm bootstrap [doctor [<id>]] [domain <id>] [product <id>] [previews <id>] [factory] [--redo <step>]`. Wizard steps in `common.ts` (common part), `product.ts` (the Production module of `bootstrap product <id>`) and `domain.ts` (per Product: `resend-domain`, `dns-records`, `restricted-resend-key`, `worker-domain`; `resendSteps(product)` is reused by `bootstrap product`, `domainSteps` adds `worker-domain` for `bootstrap domain` only: the Worker does not exist before the first deploy) over client interfaces (`clients.ts`: GitHub, Cloudflare, Neon, Resend), real adapters (`cloudflare.ts`, `resend.ts`, Zod-validated; `neon.ts` drives `neonctl`) and `fake/`. `previews.ts` is the Previews module (`previewSteps`). `github.ts` is the only module that calls `gh`. Resend is optional: before any key prompt the wizard asks once "Set up real email with Resend now?" (default: skip, keeps the outbox; `RESEND_API_KEY` in the env skips the question; no TTY defers). Setting it up prints `https://resend.com/api-keys` and asks for the key, empty = deferred. A blank credential is never re-asked in the same run (`memory.resendDeferred`, `memory.cloudflareDeclined`). No local state, no secret on disk; `doctor` only reads. The wizard (common and `domain`) ends by running the doctor with the credentials held in memory (exit code = doctor); standalone, with a TTY and no `CLOUDFLARE_API_TOKEN`/`RESEND_API_KEY` in the env, the doctor asks once (hidden, not stored); without a TTY it says `skip`.
- `src/ci/`: logic of the workflows, thin YAML around it: `image.ts`, `matrix.ts`, `skills.ts` (PR) and `deploy.ts` (plan, bundle, allowlist check, config, migrate) plus `smoke.ts` (the `main` deploy, `.github/workflows/factory-deploy.yml`; `--preview` is the smoke of a PR preview), `previews.ts` (the PR previews: gate, bindings check, Neon branch, preview config, URL, result, comment, `base`, cleanup; `factory-pr.yml` and `factory-pr-cleanup.yml`) and `neon-api.ts` (the Neon branches API, `fake/neon-api.ts` is its fake) and `vars.ts` (copies the `FACTORY_*` repo variables into `$GITHUB_ENV`, only names `config.ts` defines).
- `src/config.ts`: every setting and the label vocabulary. Any leaf is overridden by a `FACTORY_*` repo variable.
- `src/skipped-tests.ts`: after Development, a line added to a test file (`*.spec|test.ts(x)`, `e2e/`) that uses `test.fixme|skip|only`, `it|describe.skip|only`, `xit(`, `xdescribe(` fails the attempt (feedback names file:line; out of attempts = Escalation `needs-human`). Strings and comments are cut away; accepted false positives: a marker in a multi-line template literal or block comment, and a conditional `test.skip(cond)` in a test body.
- `src/guard.ts`: the deterministic guard before the lock. `src/paths.ts`: sensitive and harness paths. `src/result.ts`: the Zod schema of `result.json`.
- `src/report.ts`: PR, review, evidence and Escalation text. `src/prompts.ts` renders `prompts/*.md`.
- `prompts/`: the Stage prompts (`development`, `review`, `triage`, `pr-feedback`, `update-branch`, `retro`) plus `rules.md`, included in every one.
- `image/`: `Dockerfile` and `setup.sh` of the execution image. `src/local/`: the local container runner.
- `test/`: Vitest, driven through the CLI with fake adapters.

## Rules

- Bootstrap steps query the real state first and only add: never delete or overwrite a DNS record. Values the person must copy are logged as one plain line, not in a clack note (notes wrap).
- Behaviour changes come with a test against the fake adapters (the CLI is the seam), not against internals.
- The Factory never trusts the event payload: each run reads the current state of the forge, and `publish` checks again before writing.
- `work` has no `FACTORY_TOKEN`. The Agent env is an allowlist (`PATH`, `HOME`, Claude auth, `DATABASE_URL`, `CI`); adding a variable needs a test that proves nothing else leaks.
- Sensitive paths (`.github/workflows/`, `.agents/skills`, `.claude/`, `skills-lock.json`, `.mcp.json`) and harness paths are flagged, never refused (ADR 0012): the PR gets `harness-change` and a warning that names them (`[!WARNING]` for sensitive, `[!CAUTION]` for harness). `.claude/settings.json` only denies `pnpm bootstrap destroy`.
- Label names exist only in `src/config.ts` and the "Factory labels" table of `docs/agents/triage-labels.md`; a test keeps them equal. Change both.
- Prompts are English templates with placeholders. They call skills by name and repeat the hard rules; they never copy a skill's text.
- The image tag is a hash of the versions it installs; bump a version only after checking the official docs.
- Untrusted text (issue, comments, review threads) is wrapped in tags in prompts and never treated as instructions.

## Commands

- `pnpm bootstrap`, `pnpm bootstrap doctor`: set up (ending with the doctor, one run is enough) and check the copied repo (needs `gh` logged in; tests use the fake clients only).
- `pnpm bootstrap product <id>`: the Production module. Steps `neon-project`, `github-environment`, `database-secrets`, `auth-secret`, the four `domain` steps, `main-ruleset`, `deploy-products`; then the doctor of the Product, and only if it passes `DEPLOY_ENABLED=true`. Secrets are `<ID>_DATABASE_URL` (direct, migrations), `<ID>_DATABASE_URL_POOLED` (the Worker), `<ID>_BETTER_AUTH_SECRET`, `<ID>_RESEND_API_KEY`, in the `<id>-production` environment (restricted to the default branch), or at repo level with `FACTORY_USE_ENVIRONMENTS=false` when GitHub refuses environments. An existing ruleset that already covers the default branch (PR, no force-push, no deletion, check `verify`) is reused, never duplicated. Neon: the wizard uses neonctl's own saved login (`neonctl auth` opens the browser only when `neonctl me` shows none, so once per machine) or `NEON_API_KEY` from the env, and passes the connection strings straight to `setSecret`; it never logs out. It makes no Neon API key for production (the deploy only needs the connection strings).
- First deploy of a new Product: a push deploys only the Products it affects, so after `bootstrap product <id>` run the Deploy workflow by hand once (`gh workflow run factory-deploy.yml --ref main`); a manual run deploys every Product in `DEPLOY_PRODUCTS`. The wizard prints this line at the end.
- `pnpm bootstrap previews <id>`: the Previews module (optional, after Production). Steps `preview-environment` (`<id>-preview`, restricted like production, same `FACTORY_USE_ENVIRONMENTS` fallback), `preview-neon-project` (`<id>-preview`, default branch renamed to `base`; variable `<ID>_PREVIEW_NEON_PROJECT_ID`), `preview-neon-key` (secret `<ID>_PREVIEW_NEON_API_KEY`, minted with `neonctl api-keys create --project-id` under the run's login; when Neon refuses, one pasted key, hidden, blank = skip and remembered), `preview-kv` (KV `<id>-preview-oauth` through the Cloudflare client; variable `<ID>_PREVIEW_OAUTH_KV_ID`) and `preview-products` (id in `PREVIEW_PRODUCTS`). Then the doctor of the previews and, only if it passes, `PREVIEWS_ENABLED=true`. The one-run rules hold: a recorded variable or secret proves a step done (no Neon login, no Cloudflare prompt on a rerun), one Neon login per run and only with Neon work. The doctor shows a Previews section for a Product by presence (any preview variable, secret, environment or the id in `PREVIEW_PRODUCTS`); the Production module never fails on it.
- PR previews (`.github/workflows/factory-pr.yml`, off until `PREVIEWS_ENABLED`): `build` (PR code, no secrets) also uploads `bundle-<id>`; `preview-plan` (`previews.ts gate`: affected ∩ `PREVIEW_PRODUCTS`, author `write`+ or the event of the `preview` label put by someone with `write`+; a push removes the label); `deploy` (`main`'s checkout, the only job with Cloudflare and Neon preview secrets; allowlist check, bindings against `apps/<id>/wrangler.jsonc` of `main`, Neon branch `preview/pr-N` from `base` or "preview skipped: limit reached" at `FACTORY_PREVIEW_LIMIT` (9) open previews, migrations, `wrangler preview --name pr-N --worker-name <id> --config <preview config> --secrets-file --ignore-base-config`); `smoke` (no secrets: real sign-up, the email read at `GET /api/preview/outbox?to=`, sign-in, `/api/me`, `/mcp` 401); `preview-comment` (one comment, edited). `factory-pr-cleanup.yml` on `closed` deletes the Worker Preview and the Neon branch. The deploy of `main` migrates `base` (`preview-base`) and recreates it when missing. The outbox route exists only with `EMAIL_TRANSPORT=outbox` and `PREVIEW_OUTBOX=true`, which only the preview config sets. A change to these workflows takes effect only after it is merged (`pull_request_target`).
- `pnpm bootstrap destroy [product <id> | previews <id> | factory | common]` (`destroy.ts`; no argument = everything): only a person may run it, never an agent (the root `AGENTS.md` and `.claude/settings.json` say so). It refuses without a TTY or with `CI` set before any listing or API call, lists what disappears (the production Neon database on a `!!` line; environments with their secrets), asks to type the id (`all`, `factory`, `common`), deletes one item at a time and reports failures while it continues (exit 1). Deletes: Worker (+ Previews, Custom Domains), KVs `<id>-oauth-kv` and `<id>-preview-oauth`, Neon projects `<id>` and `<id>-preview` (never one of several with the same name), Resend domain, `<ID>_*` secrets and variables, environments, the id in `DEPLOY_PRODUCTS`/`PREVIEW_PRODUCTS` (the list, its switch and the `main` ruleset go with the last Product), `FACTORY_TOKEN`. Never the repo, issues, labels, accounts, DNS records or the workers.dev subdomain. Credentials as everywhere else (wrangler/neonctl logins, `RESEND_API_KEY` or one optional question). Delete methods of the clients are used by `destroy` only.
- `pnpm bootstrap factory`: the Factory module (`factory.ts`, after the common part). Steps `labels`, `factory-token` (the one prompt, `factory-token`, hidden: the owner's fine-grained token limited to this repo; one pre-filled link `settings/personal-access-tokens/new?...` with `contents`, `pull_requests` and `issues` as write and no `workflows`, printed once after saying the only manual step is "Only select repositories"; checked before it is stored: prefix `github_pat_` (a classic `ghp_` is refused), `GET /repos/{o}/{r}` with the token must say `permissions.push` (`TokenClient`, `token.ts`); GitHub offers no way to read a fine-grained token's permissions, so the missing `workflows` cannot be tested and the wizard only warns; three tries; `FACTORY_TOKEN` in the env or already as a secret skips the prompt), `claude-auth` (never prompted: `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` from the env, or an existing secret; both in the env stores only the OAuth one; both as secrets is a warning). Then the doctor (Factory section, no Cloudflare checks) and, only if it passes, `FACTORY_ENABLED=true`. A rerun with the secrets present asks no credential. Last, only when the doctor passed, `FACTORY_ENABLED` is on and there is a TTY, one `confirm` (`example-issue`, default No, asked again on every run): an example issue (`example.ts`). It takes the first Product of `apps/` (`select` with several; none = skip), creates a parent spec (`## Testing Decisions`) and a child (`## Acceptance criteria`: a `auth.signIn.title` override in the Product's messages, checked by its own E2E), links the sub-issue, then adds `product:<id>` (created when missing) and `ready-for-agent`, which is what starts the run. It polls `GET` every 30 s for up to 40 min (spinner; `deps.example.pollMs|timeoutMs`) until the PR `factory/issue-N` has its preview comment or finished checks (exit 0), the issue gets `ready-for-human`, the `factory-issue.yml` run fails, or the timeout. Then, pass or fail (try/finally; the first Ctrl-C stops the wait and cleans up), it prints the PR and preview URLs and asks (`choose`, `example-delete`) whether to delete the example, the default and also what Ctrl-C picks, or keep it (nothing is deleted; it prints what is left and the commands that delete it later). Deleting cancels a run still going, closes the PR without merging (so `factory-pr-cleanup.yml` deletes the Worker Preview and the Neon branch; it waits for that run), deletes `factory/issue-N`, the "The Skeleton must grow" follow-ups that mention the child, the child and the parent (`gh issue delete`), and names anything left with the command that removes it. It uses only the `gh` session (`GitHubClient`), never `FACTORY_TOKEN`. No ready PR = non-zero exit, the setup is still fine. No second GitHub account exists any more (ADR 0002).
- The Factory marker (`src/marker.ts`, `<!-- factory -->`): the Factory writes as the owner, so it knows its own texts by this hidden marker, never by the author. The write adapters add it (`marked`) to every text: issue and PR comments, PR body, reviews and their inline comments, thread replies, the Triage comment; callers do not. Readers: `openThreads` (a thread whose last comment is marked is the Factory's turn; every comment must come from a `write`+ author, so a stranger's forged marker never reaches the agent), `guard.isFactoryComment` (Triage and Waiting comments: marker plus a `write`+ author) and the `wait` job's `if` in `factory-pr-feedback.yml`. A human comment that contains the marker is ignored (accepted trade).
- `pnpm factory notify <N> --outcome ready|escalated [--updated] --url --to`: the Merge Gate notice. A `notify` job after `publish` in `factory-issue.yml` and `factory-pr-feedback.yml` runs it with the job's `GITHUB_TOKEN` (never `FACTORY_TOKEN`): the comment appears as `github-actions[bot]`, mentions who applied `ready-for-agent` (`claim` writes `requester` to `$GITHUB_OUTPUT` before the lock) or who commented, and fires no workflow.
- Factory on Actions (`.github/workflows/factory-issue.yml`, off until `FACTORY_ENABLED`): `claim` (job token, `issues: write`; `pnpm factory claim`, outputs `claimed` and `start_sha` through `$GITHUB_OUTPUT`) → `image` (the reusable image job) → `work` (the image, `contents: read` + `issues: read`, only Claude's secrets, `runs-on: vars.FACTORY_RUNNER || ubuntu-latest`, 350 min; uploads `work-out`: bundle, `result.json`, prints, `stream-json`, 14 days) → `publish` (fresh VM, `FACTORY_TOKEN`, the default branch's harness, `if: always()`: no artifact means Escalation "infra"; outputs `outcome` and `url`) → `notify`. Group `factory-<N>`, no cancel. The `work` job reads the issue with its read-only job token, which the Agent's env allowlist never passes on.
- Triage (`.github/workflows/factory-triage.yml`, label `agent:explore`, off until `FACTORY_ENABLED`): `image` → `work` (the image, read-only, Claude's auth only, `pnpm factory triage --out`) → `apply` (fresh VM, `FACTORY_TOKEN`, `pnpm factory apply --in`), meeting only in the `triage-out` artifact (`triage.json`). One global group `factory-triage` without cancel: a label event during a run replaces the pending run, which sweeps every issue still in Triage. `triage` reads only the issues whose label was put by `write`+, runs ONE session over the batch and ends with `<triage>{"issues": [...]}</triage>` (`src/triage-output.ts`: `tag` `easy-call|needs-a-human|blocked`, difficulty, files, claims, questions, approach, `door`, `seams` with what each catches and lets through, `product`, `duplicateOf`). The block is extracted with the Agent seam's resume (max 2, validator: every issue of the batch has a valid verdict; an easy-call needs a seam). Fallback, after 2 failed resumes or a timeout: each issue without a valid verdict gets `needs-a-human` (door one-way, session's last words in the comment); nothing is queued on a guess. `apply` trusts only the shape of `triage.json`: it re-reads the forge (still `agent:explore`, label by `write`+), posts the one `<!-- factory:triage -->` comment (rendered by the harness, before the label swap: `ready-for-agent` starts a run whose guard needs it), then swaps `agent:explore` → `ready-for-agent` / `ready-for-human` / `needs-info`; a duplicate is never queued (`ready-for-human`). It adds `product:<id>` only when the issue has none and `apps/<id>` exists. `pnpm factory local NN` on a ticket with Status `agent:explore` runs `triage` in the container and `apply` on the host.
- Unblock (`.github/workflows/factory-unblock.yml`, `issues: closed` + dispatch, no cron, off until `FACTORY_ENABLED`): `pnpm factory unblock` with the job token (`actions: write`, no secret) sweeps the open `ready-for-agent` issues, runs the guard on each and dispatches `factory-issue.yml` for those it accepts. Before the sweep, `--issue N` (the closed issue of the event, a hint: the forge says if it is closed) removes `in-progress` from it, so a merged Factory PR does not leave the label behind; the job has `issues: write` for that. Still-blocked ones get no comment (the guard wrote "Waiting on…" on `labeled`); other refusals are left to `claim`. A failed dispatch does not stop the sweep (exit 1 at the end).
- PR flows (`work <N> --flow pr-feedback|update-branch --pr <n>`, then `publish <N> --pr <n>`; `commands/pr-claim.ts` guards both): `.github/workflows/factory-pr-feedback.yml` (`pull_request_review: submitted`, `pull_request_review_comment`, `issue_comment`) is `wait` (job with `sleep 180` in group `factory-feedback-<PR>`, `cancel-in-progress: true`; a submitted review skips the sleep) → `claim` (`pnpm factory pr-feedback --pr --actor`: actor with `write`+, PR open on `factory/issue-N`, issue `in-progress`, at least one open thread) → `image` → `work` → `publish`. A thread is open until a Factory-marked comment has the last word (the Factory never resolves one). `work` merges the base branch first (an agent resolves conflicts, `update-branch.md`), then Development with `pr-feedback.md` (first attempt; `<replies>` block: address, decline, defer or answer per thread; a round of declines, defers and answers makes no commit and skips Review), Review, E2E; `publish` posts the replies in their threads (`Address: …`), and after the 5 failures comments on the PR and sets `ready-for-human` without making it a draft. `factory-update-branches.yml` (`push` on the base branch) runs `pnpm factory update-branch --scan` (`git merge-tree --write-tree` per `in-progress` issue with an open PR) and dispatches itself (`workflow_dispatch`, `issue`) only for the conflicting ones; that run merges with no agent when clean (conflict: the agent, "preserve both intents, do not invent new behaviour"), runs Verify and enters the normal loop only if it fails; it runs no Pull Request Stage and leaves the PR body alone. Both share the group `factory-<N>` on `work`; the guarantee is the lease (`Run discarded` when the branch moved).
- Automatic Retro (`.github/workflows/factory-retro.yml`, off until `FACTORY_ENABLED`, and with `FACTORY_RETRO_ENABLED=false`; `src/commands/retro.ts`, `src/retro-output.ts`): `publish` dispatches it after every Escalation (a failed dispatch is logged, never fails the Escalation), and `pull_request_target: closed` starts it for a Factory PR of this repository. `collect` (job token, read-only, `actions: read`) goes on for a closed PR only when a writer left an unmarked thread or review, then writes `retro-in`: `issue.md` (writers' comments), `pull-request.md` (writer-only threads and reviews), `runs/<id>/` (each run's `work-out` artifact, found by `#N` or the issue's/PR's title in the run title: `GitHubRunLogs`, `gh run download`) and `sources.json` → `work` (the image, read-only, Claude's auth only; one session that reads `.agents/skills/retro/SKILL.md` and ends with `<retro>{"summary", "candidates": [{category, severity, title, proposal, evidence[]}]}</retro>`; no valid block after 2 resumes fails the run, nothing is published) → `publish` (`FACTORY_TOKEN`): creates `Retro: #N <title>` with `needs-triage` + `retro`, or edits the open one carrying `<!-- factory:retro:issue-N -->` and the Factory marker; no candidate = one comment on the PR (or the issue). It never applies `ready-for-agent`. The Review ends its summary with "Rules this review wanted and could not find", which the Retro reads.
- `pnpm bootstrap domain <id>`, `pnpm bootstrap doctor <id>`: a Product's domain. Reads `domain` from `apps/<id>/product.config.ts` (never rewrites it). Needs `RESEND_API_KEY` (full access, or it is asked) and the one Cloudflare token (template URL in `common.ts`: Workers Scripts Edit, Workers KV Storage Edit, Account Settings Read, DNS Edit, Zone Read; no Workers Routes, the Custom Domain needs only Workers Scripts Write; older tokens must be recreated). A pasted token is checked with read-only calls (verify, scripts, KV, account, zones, DNS records) and a refused one is named and asked again without being stored; the probes cannot tell edit from read, the first real write does. Without the zone in the account, DNS records are printed as plain lines; without the Worker, the Custom Domain waits for the first deploy.
- `pnpm --filter @factory/harness test|typecheck`
- `pnpm factory local <NN> [--issues <dir>]`: run an issue on this machine in a throwaway container (needs Claude auth).

## Cloudflare credential (never asked twice)
- The Cloudflare API token is collected once, by the `cloudflare-token` step of the common part, and only while the `CLOUDFLARE_API_TOKEN` CI secret does not exist (an explicit `--redo cloudflare-token` replaces it). `promptMainToken` is called nowhere else.
- Every other Cloudflare call (`cloudflareHandle`: previews KV, `dns-records`, `worker-domain`; `workers-dev`; the doctor) takes its credential from `cloudflareCredential` in `common.ts`, in this order: this run's memory, `CLOUDFLARE_API_TOKEN` in the env, wrangler's saved login (`wrangler auth token --json`, via `wrangler.ts`; wrangler 4.151.2 docs read 2026-10-20: refreshes an expired OAuth token itself). With none, steps that may change things run `wrangler login` once (browser; wrangler keeps it, like neonctl); the doctor and the `check`s never log in. The token stays in memory: never logged, written or sent to the forge.
- The account id is `CLOUDFLARE_ACCOUNT_ID` from the env or the only account the credential sees; with several it fails naming `CLOUDFLARE_ACCOUNT_ID`, it never asks.
- wrangler's OAuth scopes have no DNS: when listing or creating DNS records is refused (`CloudflareRefused`), `dns-records` prints each record on one unwrapped line plus a "NOT done" note and returns without prompting; run it again after creating them by hand.
