# 14: Produção de um Product

Spec: [../spec.md](../spec.md)

**What to build:** `pnpm bootstrap product example` configura a produção do `example`, e todo merge na `main` passa a fazer deploy dos Products afetados pelo Actions, com smoke de login real. O `example` está no ar num `workers.dev`, e um `exceededCpu` no hash apareceria como deploy vermelho.

**Blocked by:** 07, 12, 13

**Status:** ready-for-agent

- [ ] Módulo Produção: projeto Neon `<id>` (procura antes de criar) com key restrita, domínio do Resend adiável com os registros DNS mostrados, secrets `<ID>_`, o id em `DEPLOY_PRODUCTS`, `DEPLOY_ENABLED` ligado depois do `doctor`.
- [ ] Environments `<id>-production`/`<id>-preview` restritos à `main` e ruleset na `main` (PR obrigatório, sem force-push nem exclusão, check `verify`), com queda para secrets no repo e `FACTORY_USE_ENVIRONMENTS=false` quando a API recusar.
- [ ] Workflow de deploy da `main`: `build` sem secrets → `deploy` (código da `main`, config gerado com o id, migrations do Skeleton e do Product, `wrangler deploy --name <id>`, KV de produção pelo provisionamento automático) → `smoke` (login real, 401 com `WWW-Authenticate` no `/mcp`) (seam 7).
- [ ] O deploy da `main` também migra o branch `base` do preview quando o módulo Previews existir.
- [x] Testes do módulo contra os falsos: queda para o nível do repo, prefixo `<ID>_` (seam 8).
- [ ] Deploy de teste do `example` pelo Actions.
- [ ] Medidos também aqui, vindos dos tickets 03 e 04: 429 do rate limit por IP atrás da Cloudflare (`cf-connecting-ip`); linhas do `RateLimiter` dentro das cotas de DO do Free; CPU do render do email no Worker.

Código implementado (2026-10-20, branch `ticket-14`). Nenhum critério além do dos testes do módulo foi marcado; abaixo, o que falta em cada um.

**Módulo Produção** (`pnpm bootstrap product <id>`, `.factory/src/bootstrap/product.ts`). Etapas, todas idempotentes e com `--redo`: `neon-project`, `github-environment`, `database-secrets`, `auth-secret`, as quatro do `domainSteps` (adiáveis), `main-ruleset`, `deploy-products`. Termina com o `doctor <id>` (seção Production nova) e só então liga `DEPLOY_ENABLED=true`; se o doctor falha, a variável fica desligada e o comando diz.
- Secrets que o módulo grava (nomes): `<ID>_DATABASE_URL` (conexão direta, migrations), `<ID>_DATABASE_URL_POOLED` (o `DATABASE_URL` do Worker), `<ID>_BETTER_AUTH_SECRET` (32 bytes aleatórios; um `--redo auth-secret` encerra as sessões), e `<ID>_RESEND_API_KEY` (pelo `restricted-resend-key`, só se o domínio do Resend existir). Variáveis: `DEPLOY_PRODUCTS` (acrescenta o id sem tirar os outros), `DEPLOY_ENABLED`, `FACTORY_USE_ENVIRONMENTS=false` só na queda. Os secrets comuns (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`) continuam no repo, sem prefixo.
- Environment `<id>-production` restrito à branch padrão (política de branch custom). Se a API recusar (403, 404 ou 422), os secrets vão para o repo e `FACTORY_USE_ENVIRONMENTS=false`; rodar o passo de novo depois de trocar de plano volta para `true`. O `GitHubClient` ganhou `listEnvironments`, `upsertEnvironment`, `listRulesets`, `createRuleset` e `setSecret/listSecrets` com `environment`.
- Ruleset: um existente de qualquer nome e id que cubra a branch padrão (ativo, `deletion`, `non_fast_forward`, `pull_request`, check `verify`) conta como feito; o `main` à mão (id 25500591) é reconhecido e não duplicado. Um que não tenha o check `verify` não conta e o passo cria o seu. Recusa da API: avisa e pula.
- **Decisão (Neon, com o usuário):** nada de key colada nem integração do GitHub. O adaptador (`neon.ts`) dirige o `neonctl` (já devDependency) com `--config-dir` descartável (`mkdtemp`): `auth` (navegador), `orgs list`, `projects list --org-id`, `projects create --name <id> --no-secrets`, `connection-string [--pooled]`, sempre `-o json` onde há JSON. Várias orgs: pergunta e passa `--org-id` em tudo. Projetos com o mesmo nome: pergunta qual usar, nunca apaga. As connection strings vão do stdout do CLI direto para o `setSecret` (stdin do `gh`), nunca para disco, argv ou log; o `credentials.json` nunca é lido. No fim (`finally`, e no `exit` para Ctrl+C, inclusive o do clack) roda `neonctl logout --config-dir D` e apaga D. `NEON_API_KEY` no ambiente segue aceita (sem login, nunca guardada) para uso sem terminal. O `services.ts` com `NeonCli` antigo e seu teste saíram.
- **Decisão (key restrita ao projeto):** não criada neste ticket. O deploy de produção só precisa das connection strings (migrations usam `<ID>_DATABASE_URL`); `wrangler` usa o token da Cloudflare. O critério "com key restrita" fica desmarcado: quem precisa é o módulo Previews (ticket 15), que ramifica o banco pela API do Neon e fará `neonctl api-keys create --project-id` (não verificado sob OAuth: a doc diz que a primeira key vem do Console; fallback: colar uma).
- `neondb_owner`/`neondb` são passados explicitamente ao `connection-string` (padrão de um projeto novo); um projeto antigo com outro papel precisaria de ajuste. Pending (human): rodar na conta real; o adaptador do `neonctl` só foi exercitado com um executor falso (argumentos, env mínimo, logout e remoção da pasta), e o `neonctl auth/logout --config-dir` não foi rodado de ponta a ponta.

**Workflow** `.github/workflows/factory-deploy.yml` (push na `main` + `workflow_dispatch`; `image` com `if: vars.DEPLOY_ENABLED == 'true'`, os outros dependem dele e aparecem pulados). Jobs: `plan` (imagem; `deploy.ts plan`: afetados pelo turbo ∩ `DEPLOY_PRODUCTS`; manual = todos os listados) → `build` por Product (imagem, sem secrets, `contents: read`, aceita `vars.FACTORY_RUNNER`; `turbo run build --filter` roda o `generate` antes, sem ele o Vite falha; sobe `apps/<id>/dist` + `drizzle/`) → `deploy` por Product (VM nova, checkout do `github.sha`, `pnpm install --frozen-lockfile --ignore-scripts`, artifact em `$RUNNER_TEMP` com allowlist (`worker/**`, `migrations/**` só `.sql`/`.json`/`.gitkeep`, sem symlink), config gerado com o id ao lado do build (tira `secrets`, `dev`, `configPath`), migrations do Skeleton e do Product via `migrateDatabase` contra `<ID>_DATABASE_URL`, `wrangler deploy --name <id> --secrets-file`, KV pelo auto-provisionamento; `CLOUDFLARE_API_BASE_URL` fixo; environment `<id>-production` salvo se `FACTORY_USE_ENVIRONMENTS == 'false'`) → `smoke`. É o único job com secrets. Conferido localmente: `bundle`, `verify-bundle` e `config` sobre um build real do `example`, e `wrangler deploy --dry-run --config ... --name shop` aceitou o config. A URL do deploy segue para o `smoke` como artifact de uma linha (outputs de job em matrix colidiriam entre Products). Ações novas fixadas por SHA, lidas com `git ls-remote` em 2026-10-20: `actions/upload-artifact` v7.0.2, `actions/download-artifact` v8.0.2.

O sign-up exige verificar o email, que em produção vai pelo Resend e não tem caixa para ler, e o job `smoke` não tem secrets (então nenhuma conta de smoke para entrar). Por isso o critério do workflow (login real) e o de "login real sem `exceededCpu`" ficam desmarcados.
